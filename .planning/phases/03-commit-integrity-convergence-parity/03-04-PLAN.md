<objective>
Wire the WIRE-03 and CONV-01 validators into the two receive-side seams: the inbound commit
branch in `ingest.ts` and the candidate-edge construction in `fork-recovery.ts`. Both use the
pre/post-apply reconciliation mechanism RESEARCH resolves: call `processMessage` once, capture
the commit's own `AppDataUpdate` proposals through a thin wrapper around the existing admin
callback, then validate `(parentState, newState, capturedProposals)` before the result is
committed to canonical state or turned into a branch edge.

Purpose: criterion 1 demands the check behave identically on inbound and convergence/replay.
This plan makes two of the three seams identical by construction — they call the same
`validateCommitLegality` adapter and differ only in what they do with a violation.
Output: a proposal-capture wrapper, the inbound rejection gate, the replay drop-edge gate, and
a seam-parity test file.
</objective>

  <action>
Add to `src/engine/admin-policy.ts` a new named export:

`export function withCapturedProposals(inner: IncomingMessageCallback): { callback: IncomingMessageCallback; take(): Proposal[] }`

`callback` delegates every decision to `inner` unchanged — this is a decorator, NOT a policy change; the MIP-03 admin gate, the account-identity-proof check, and the admin-self-remove guard all keep their exact current behavior. Its only extra effect: when `incoming.kind === "commit"`, it appends `incoming.proposals.map((p) => p.proposal)` to a private buffer BEFORE returning `inner(incoming)`, so proposals are captured even for a commit the admin gate rejects.

`take()` returns the buffered proposals and clears the buffer, so a caller looping over several commits with one shared callback reads exactly the proposals of the message it just processed. Document that contract: callers MUST call `take()` immediately before each `processMessage` (to discard anything stale) and again immediately after it returns (to read the commit's own proposals).

Give the export a JSDoc block explaining WHY it exists: ts-mls has no OpenMLS `StagedCommit` equivalent — `processMessage` returns the fully-applied `newState` in one step and `IncomingMessageCallback` is the only pre-apply hook, but it never sees the resulting `GroupContext`. The callback is therefore used purely as a side channel for the attribution rule; the validators run after `processMessage` returns. Cite `refs/mdk/crates/cgka-engine/src/app_components.rs` `validate_app_component_integrity_for_staged_commit` as the algorithm this feeds, and state explicitly that no validation logic may be added inside the callback (Pitfall 1).

Do not modify `createAdminCommitPolicyCallback` itself.
</action>
