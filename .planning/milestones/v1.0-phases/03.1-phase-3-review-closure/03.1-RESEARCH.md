### Pattern 1: Irreversible confirmation boundary

**What:** Split failure handling into pre-confirm failures, which reject and roll back pending state, and post-confirm ancillary failures, which must return confirmation plus notifications and a typed failure status. [VERIFIED: current review CR-03; upstream `refs/marmot` commit `4a2bc65`]

**When to use:** Both self-update and group-evolution commit paths; proposal behavior can remain unchanged because it derives no state notifications. [VERIFIED: `group-runtime.ts`]

```typescript
// Shape is illustrative; exact names remain planner discretion.
type ConfirmedCommitResult = {
  response: Record<string, PublishResponse>;
  notifications: StateNotification[];
  persistence: { kind: "saved" } | { kind: "failed"; error: unknown };
  welcomeDelivery?: { kind: "delivered" } | { kind: "failed"; error: unknown };
};
```

### Pattern 2: Single-flight idempotent realization

**What:** Cache the in-flight Promise before the first await; all concurrent callers await it. Clear it on failure so a later call retries. Keep the durable marker as restart idempotency and the Promise as same-instance concurrency idempotency. [VERIFIED: current review WR-01]

### Pattern 3: Attach listeners before state-derived effects

**What:** `load()` hydrates only; `get()`/manager adoption tracks the instance, then triggers reconvergence and realization, then emits `loaded`. If an API must return only after reconvergence, put the ordering in one registry orchestration method rather than letting callers compose it inconsistently. [VERIFIED: current CR-01 call chain]

### Anti-Patterns to Avoid

- **Rejecting after confirmation:** hides already-ledgered notifications and encourages unsafe retry. [VERIFIED: CR-03]
- **Returning only relay responses from commit helpers:** loses notification metadata at alternate call sites such as auto-commit. [VERIFIED: CR-02]
- **Appending notifications to the original `autoCommit` result ad hoc:** the locked context requires the same consumer-facing applied-notification shape used elsewhere. [VERIFIED: `03.1-CONTEXT.md`]
- **Mutex via runtime-specific primitives:** breaks cross-runtime compatibility; one cached Promise is sufficient. [VERIFIED: project constraints]
- **Reordering only `GroupRegistry.get` while leaving manager adoption/load paths separate:** recreates CR-01 at another construction seam. [VERIFIED: context and registry call-chain inspection]

## Common Pitfalls

### Pitfall 1: Swallowed auto-commit failure conflates pre- and post-confirm errors
**What goes wrong:** The existing blanket `catch {}` is correct only for publish failure that rolled pending state back. A post-confirm save/Welcome failure cannot be swallowed as if the auto-commit were retryable. [VERIFIED: `marmot-group.ts`, CR-03]
**How to avoid:** Give runtime results a committed discriminator; retry only pre-confirm failures. Test that canonical epoch advances once and a second intent is not published. [VERIFIED: review recommendation]

### Pitfall 2: `get()` dedup does not make a public method idempotent
**What goes wrong:** Two explicit calls to `realizeRemovalIfNeeded()` can overlap their store reads and emit twice. [VERIFIED: WR-01]
**How to avoid:** Force overlap with a deferred `getItem` test, call via `Promise.all`, and assert one get/set/event sequence. [VERIFIED: codebase testing pattern]

### Pitfall 3: Testing a removed tip without a competing tree misses CR-01
**What goes wrong:** The post-track realization test passes, but `load()` reconvergence consumes the marker first only when the tree has multiple tips. [VERIFIED: CR-01]
**How to avoid:** Persist an actual multi-tip `GroupHistoryTree`, load through `GroupsManager`/registry, and assert exactly one manager-level `removed` plus marker. [VERIFIED: review fix]

### Pitfall 4: Delivering a withdrawal for an unseen application
**What goes wrong:** Auto-commit confirms and records notifications, but ingest yields only `autoCommit`; later rewind yields `stateInvalidated`. [VERIFIED: CR-02]
**How to avoid:** Regression must record delivered commit digests and assert every withdrawn digest was previously delivered. [VERIFIED: review fix]

### Pitfall 5: Reference drift changes the correct solution
**What goes wrong:** Local `refs/marmot` is one relevant commit behind and `refs/mdk` is far behind; planning solely from pinned source misses the new durability contract and recent MDK implementation patterns. [VERIFIED: `git fetch`/`log`]
**How to avoid:** First plan task fast-forwards both submodules, reviews relevant diffs, and commits only pointer bumps. [VERIFIED: `AGENTS.md`]

## Open Questions (RESOLVED)

1. **What exact post-confirm failure API does current MDK use?**
   - **Exact MDK contract:** `Engine::do_confirm_published_with_fanout` clones the accepted `OutboundFanout`, advances the clone with `OutboundFanout::mark_mls_confirmed`, and writes the OpenMLS merge, Marmot group mirror, notification-origin records, and confirmed fanout in one `StorageProvider::with_transaction` call. A persistence failure therefore returns `EngineError` *before* `EpochManager::confirm_publish` consumes the pending slot; it is a retryable confirmation failure, not a successful confirmation followed by an ancillary save failure. [VERIFIED: `refs/mdk/crates/cgka-engine/src/publish.rs::do_confirm_published_with_fanout`; `refs/mdk/crates/traits/src/transport_adapter.rs::mark_mls_confirmed`]
   - After that transaction commits, MDK advances the in-memory lifecycle and returns `GroupEvent`; post-confirm application projections are accumulated separately in `SessionEffects`/`AccountDeviceEffects`. [VERIFIED: `refs/mdk/crates/cgka-engine/src/publish.rs::do_confirm_published_with_fanout`; `refs/mdk/crates/marmot-account/src/runtime.rs::AccountDeviceEffects`]
   - `OutboundFanout::stage_with_post_confirmation_welcomes` durably freezes exact Welcome artifacts and marks them pending. `AccountDeviceRuntime::resolve_outbound_fanout_mls` confirms MLS first, then releases those Welcomes; per-recipient terminal failures are returned as typed `WelcomeDeliveryFailure` entries in `AccountDeviceEffects.welcome_failures`, while unresolved target state remains in the durable fanout for exact-byte retry. The caller redelivers through `AccountDeviceRuntime::redeliver_welcome`, not by re-committing. [VERIFIED: `refs/mdk/crates/traits/src/transport_adapter.rs::OutboundFanout`; `refs/mdk/crates/marmot-account/src/runtime.rs::resolve_outbound_fanout_mls`; `AccountDeviceEffects::welcome_failures`; `redeliver_welcome`]
   - **CR-03 model for marmot-ts:** retain the phase's smaller architecture but copy the semantic split. `GroupPublishResult` must always represent an acknowledged-and-confirmed commit with its exact `notifications`; `publishFailed` remains exclusive to pre-confirm relay failure. Because marmot-ts lacks MDK's transactional shared store, a later `save()` rejection is a typed `persistence` ancillary failure on that confirmed result with `retryPublication: false`. Welcome failure is a distinct typed `welcome` ancillary failure, also with no re-commit/republication instruction. Do not reject away the confirmed result. [VERIFIED: current `GroupRuntime` call chain; MDK contract above; `refs/marmot/protocol-core/durability.md` application-effect observation boundary]
   - **Plan consequence:** Plan 03.1-02 remains directionally valid, but its text must stop implying that MDK itself returns a post-confirm persistence-failure result. It must explicitly describe the TypeScript `save()` status as an architecture-specific projection of MDK's atomic durability rule, and keep separate persistence and Welcome ancillary fields. [VERIFIED: plan/source comparison]

2. **Should `GroupRegistry.load()` remain public as a hydration-only primitive?**
   - **Resolved: hydration-only.** MDK's `hydrate_one_stored_group` loads, validates, repairs interrupted durable transitions, restores lifecycle state, and calls `schedule_pending_convergence_group` when stored convergence input exists; it does not run `advance_convergence`. The runtime performs convergence later through the separately observable/scheduled `AccountDeviceRuntime::advance_convergence` path. [VERIFIED: `refs/mdk/crates/cgka-engine/src/engine.rs::hydrate_one_stored_group`; `schedule_pending_convergence_group`; `refs/mdk/crates/marmot-account/src/runtime.rs::advance_convergence`]
   - Current marmot-ts violates that separation: `GroupRegistry.load()` builds the group and directly awaits `group.reconverge()` before any `GroupRegistry.track()` listener exists; `get()` only tracks afterward. Direct test callers of `load()` inspect hydrated history/state and do not establish a public event subscription contract. [VERIFIED: `src/client/group-registry.ts::load/get`; repository call-site grep]
   - **Listener-safe CR-01 ordering:** `load()` performs store read, state/tree/retained hydration, and `build()` only. Registry-owned activation then performs `track()`'s cache insertion and listener attachment first, awaits `group.reconverge()` when the hydrated tree has multiple tips, awaits `group.realizeRemovalIfNeeded()`, emits `loaded`, and only then resolves `get()`. Reconvergence must not remain inside `load()`, and removal realization must not run before the listener is installed. [VERIFIED: MDK split above; current CR-01 call chain]
   - `adoptClientState`, `create`, and other newly built-group paths have no persisted competing tree to reconverge, but they must continue entering through the same listener-first tracking boundary before any removal realization or lifecycle event. `destroy()` and `leave()` currently call public `load()` directly when uncached; because hydration-only groups are intentionally untracked, those destructive one-shot paths may remain uncached, but they must not rely on load-time reconvergence. [VERIFIED: `src/client/groups-manager.ts::adoptClientState/create/destroy/leave`]
   - **Plan consequence:** Plan 03.1-01 should replace the ambiguous phrase “implement the recorded load resolution” with the exact split above and add an explicit activation helper/ownership seam (`load -> track listeners -> reconverge -> realize -> loaded`). Its regression must assert `removed` precedes `loaded` and both occur after listeners exist. [VERIFIED: plan/source comparison]
