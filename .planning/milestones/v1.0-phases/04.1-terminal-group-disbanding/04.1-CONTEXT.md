# Phase 04.1: Terminal Group Disbanding - Context

**Gathered:** 2026-09-06
**Status:** Ready for planning

<domain>
## Phase Boundary

Implement the `marmot.group.lifecycle.v1` application component and its terminal `disbanded` value, force every valid disband candidate through bounded convergence even on a linear edge, and make the selected terminal state durable and observable. This phase does not add general lifecycle variants, resurrection, multi-device behavior, or release-matrix work.

</domain>

<decisions>
## Implementation Decisions

### Durable Terminal State and Public Contract

- **D-01:** Persist canonical `disbanded` state so restart cannot make a terminal group live again. — **Reversibility:** one-way — changing the persisted terminal contract later would require a storage migration and could resurrect groups downstream code already treats as permanently inactive.
- **D-02:** Expose the terminal state through the public group status/view surface and emit a single lifecycle event when canonical disbanding occurs.
- **D-03:** Reject every outbound operation after canonical disbanding with a typed terminal reason rather than a generic lifecycle error.
- **D-04:** Classify subsequent inbound input consistently with existing removed/inactive handling; it must not reopen convergence or produce application output.

### Convergence Boundary

- **D-05:** A valid disband-changing Commit always opens or joins a bounded convergence pass, including a linear edge with no competing branch.
- **D-06:** Forced admission must not restart the convergence deadline, resnapshot `pass_base_epoch`, or add any scoring preference for the disband candidate.
- **D-07:** Terminalization occurs only after the disband branch is selected canonically; a losing or withdrawn disband candidate has no terminal effect.

### the agent's Discretion

- Exact names of the public status/event and typed rejection discriminant, provided they match established named-export and discriminated-union conventions.
- Persisted codec/versioning shape and migration mechanics, provided older live state remains readable and canonical terminal state cannot degrade on restart.
- Test and plan decomposition, including whether terminal inbound classification reuses the existing removed reason verbatim or a terminal-specific member of the same inactive family.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `src/core/components/` provides component codecs, dictionary integrity validation, and colocated byte tests.
- `src/core/group-lifecycle.ts` is the lifecycle FSM and outbound safety gate.
- `src/engine/group-engine.ts`, `src/engine/fork-recovery.ts`, and Phase 4's bounded scheduling machinery provide the forced-pass and canonicalization seams.
- Existing removed-group handling in the engine/client layers provides the terminal input and public inactive-state analog.

### Established Patterns
- Protocol codecs are pure, binary data is `Uint8Array`, and persisted formats are explicitly versioned with backward decoding.
- Expected lifecycle outcomes use discriminated unions; client observability is emitted only after durable state is established.
- Publish-before-apply and canonical branch selection remain mandatory before state mutation becomes externally visible.

### Integration Points
- Add the lifecycle component to application-data dictionary encoding and integrity checks.
- Detect a valid disband transition during Commit admission and signal the existing bounded convergence scheduler without modifying scoring.
- Persist terminal state with the canonical group snapshot, then update public view/status, outbound guards, events, and inactive inbound classification.

</code_context>

<specifics>
## Specific Ideas

- Treat disbanding as permanent group death: durable, visible, and impossible to undo through later transport replay.
- Reuse the semantic shape of removed/inactive handling for post-terminal traffic while retaining a typed reason that lets downstream clients distinguish disbanding.

</specifics>
