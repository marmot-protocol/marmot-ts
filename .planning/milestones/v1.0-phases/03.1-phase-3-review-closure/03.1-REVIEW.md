## Critical Issues

### CR-01: A late concurrent cache hit bypasses in-flight group activation

**Classification:** BLOCKER  
**File:** `src/client/group-registry.ts:257-292,331-357`  
**Issue:** `track()` writes the group into `#groups` and emits `updated` before awaiting `reconverge()` and `realizeRemovalIfNeeded()`. While either await is pending, a new `get(id)` reads `#groups` at line 335 and returns that group without consulting `#groupLoadPromises`. If activation later rejects, the first caller sees the error and cleanup disposes the exact instance, but the late caller has already received the partially activated (and subsequently disposed) object. Application code can send through stale canonical state, miss removal realization, or retain a group that the registry no longer tracks. The new concurrent tests call both `get()` operations before `load()` resolves, so both happen to share `#groupLoadPromises` and do not cover this cache-hit interleaving. Emitting `updated` before activation completes exposes the same partial instance through `loaded` observers.

**Fix:** Make pending activation part of the cache contract. Prefer an in-flight load/activation promise before any `#groups` cache hit, and do not emit `updated` until activation succeeds; alternatively keep the group outside `#groups` until `reconverge()` and removal realization complete. Add a controlled-promise regression that pauses `reconverge()` or marker lookup after `track()` installs the group, calls a second `get(id)`, then rejects activation and proves both callers reject and neither can obtain the disposed instance.

## Warnings

### WR-01: Safe removal dispatch drops EventEmitter listener contexts

**Classification:** WARNING  
**File:** `src/client/group/marmot-group.ts:753-761`  
**Issue:** `#emitRemovedSafely()` obtains bare functions from `listeners("removed")` and invokes each as `listener(this)`. EventEmitter3 supports `on(event, fn, context)` and normally calls `fn` with the registered context as `this`; the manual dispatch discards that context. Existing consumers that use the documented EventEmitter context form will observe different callback behavior specifically for `removed`, and the throwable-listener regression does not exercise context or compare behavior with the other lifecycle events.

**Fix:** Preserve EventEmitter3's listener records/context while isolating failures, for example by adding a small callback registry owned by `MarmotGroup`, or by exposing a protected safe-dispatch helper that retains `{ fn, context, once }` metadata. Add coverage for `on("removed", listener, context)` and `once("removed", listener, context)` alongside exception isolation.
