### Locked Decisions

- **D-01:** Persist canonical `disbanded` state so restart cannot make a terminal group live again. — **Reversibility:** one-way — changing the persisted terminal contract later would require a storage migration and could resurrect groups downstream code already treats as permanently inactive.
- **D-02:** Expose the terminal state through the public group status/view surface and emit a single lifecycle event when canonical disbanding occurs.
- **D-03:** Reject every outbound operation after canonical disbanding with a typed terminal reason rather than a generic lifecycle error.

- **D-06:** Forced admission must not restart the convergence deadline, resnapshot `pass_base_epoch`, or add any scoring preference for the disband candidate.
- **D-07:** Terminalization occurs only after the disband branch is selected canonically; a losing or withdrawn disband candidate has no terminal effect.

## Summary

Phase 04.1 should be planned as three coupled changes: exact lifecycle-component legality, a special admission signal into the already-built Phase 4 bounded scheduler, and a durable terminal tombstone/public contract. The wire component is `0x800c`; its value is exactly one byte (`0x00` active, `0x01` disbanded), and all other or trailing-byte encodings are invalid. New groups require it in active state, while older groups may omit it and cannot disband until an admin atomically enables both the component and its required-component declaration. [VERIFIED: `refs/marmot/app-components/group-lifecycle-v1.md`; `refs/marmot/protocol-core/group-setup.md`]

The central safety rule is “candidate first, terminal state only after canonical selection.” A valid disband Commit must never take the ordinary direct-linear apply path. Admission opens or joins the same bounded pass used by convergence and forces protocol lifecycle `Stable -> Recovering` even without a fork, but does not reset timers, change the pass base, or affect scoring. If the selected branch is active, normal stable operation resumes; only a selected branch ending in disbanded creates the tombstone, emits the one terminal event, and stops all later processing. [VERIFIED: `refs/marmot/protocol-core/convergence.md`; `refs/mdk/crates/cgka-engine/src/message_processor/ingest.rs`; `refs/mdk/crates/cgka-engine/src/distributed_convergence.rs`]

The current TypeScript architecture has most necessary seams: strict component descriptors and integrity validation, candidate history and canonical branch selection, immutable bounded-pass deadlines, state-notification ledgers, a restart-stable removed marker, and public group manager events. What it lacks is a lifecycle-v1 codec/validator, terminal candidate metadata, a `Disbanded` FSM state, and a versioned terminal record independent of live `ClientState`. Do not encode terminality only inside serialized MLS state: the spec requires live MLS and routing state to be released after selection, so terminal identity must survive without a usable live snapshot. [VERIFIED: `src/core/components/dictionary.ts`; `src/core/components/integrity.ts`; `src/engine/group-engine.ts`; `src/client/session/group-session.ts`; `refs/marmot/app-components/group-lifecycle-v1.md`]

**Primary recommendation:** Add a pure lifecycle component/Commit validator first, then carry a `disbands` candidate flag plus actor/digest through existing history/convergence, and atomically replace live persistence with a versioned terminal tombstone before exposing `status: "disbanded"` or emitting `disbanded`. [VERIFIED: current TypeScript architecture and MDK transaction ordering]

## Exact Protocol Semantics

### Component state and enablement

- Define `GROUP_LIFECYCLE_COMPONENT_ID = 0x800c` and name `marmot.group.lifecycle.v1`; add it to supported leaf capabilities and to default required/new-group component state as active. [VERIFIED: `refs/marmot/app-components/group-lifecycle-v1.md`; `refs/marmot/protocol-core/group-setup.md`]
- Decode only one byte: `0x00 -> active`, `0x01 -> disbanded`; reject empty, unknown, and trailing bytes. Use an enum-like named-export object plus literal union, consistent with repository conventions. [VERIFIED: lifecycle spec; `src/core/components/*` codec patterns]
- A legacy group with neither lifecycle state nor required ID remains valid and cannot disband. Enabling is one admin Commit that adds active state (if absent) and adds `0x800c` to required IDs. That Commit is valid only when **every leaf in the resulting epoch advertises support for `0x800c`**; one unsupported resulting leaf rejects the whole enablement Commit, with no partial state change. Enablement emits no disband notification. [VERIFIED: `refs/marmot/app-components/group-lifecycle-v1.md`, “Enablement for existing groups”]
- Once lifecycle-v1 is required, state and required declaration are immutable except `active -> disbanded`; removing the state or required ID is invalid. [VERIFIED: lifecycle spec; existing component integrity validator]

### Valid disband Commit predicate

The planner should create one pure function that consumes authenticated parent facts, resulting facts, exact committer leaf/account, and ordered resolved proposals. It returns either `{ kind: "notDisband" }`, `{ kind: "validDisband", actor }`, or a typed violation. A candidate is valid only if all conditions hold: [VERIFIED: lifecycle spec; MDK `validate_disband_commit_shape`]

1. Parent requires `0x800c` and carries active state; result carries disbanded. [VERIFIED: lifecycle spec]
2. Authenticated committer is an active admin in the candidate parent. Authorization is parent-relative, never current-tip-relative. [VERIFIED: lifecycle and convergence specs]
3. Resulting admin list is exactly the committer's Marmot account identity, and the Commit includes a full admin-policy replacement even if already sole admin. [VERIFIED: lifecycle spec]
4. Every parent leaf except the exact committing leaf is removed. This includes sibling leaves belonging to the same account. A single-leaf group therefore has zero Removes. [VERIFIED: lifecycle spec]
5. Exactly one inline lifecycle update and exactly one inline admin-policy update exist; lifecycle-by-reference or standalone proposal is invalid. [VERIFIED: lifecycle spec; MDK app-components validation]
6. No Add, Update, PSK, ReInit, ExternalInit, GroupContextExtensions, AppEphemeral, Custom, unrelated AppDataUpdate, or other proposal is present. Normal MLS/Marmot invariants still apply. [VERIFIED: lifecycle spec]

### Admission and selection

- Detect valid disbanding only after MLS authentication, account proof, component integrity, admin/leaf coupling, and lifecycle Commit-shape validation against the candidate parent. Invalid input never opens recovery. [VERIFIED: convergence spec; MDK ingest ordering]
- Record candidate identity using exact MLS Commit bytes/digest, authenticated actor, source epoch/parent, and a disband marker before scheduler admission. Do not infer terminality later from transport tags. [VERIFIED: convergence spec; MDK `DisbandCandidate`]
- If no pass exists, open it once using the existing monotonic clock and current canonical base. If a pass exists, join it and refresh quiescence only when this is genuinely new selection-relevant input. Never change `openedAtMs`, `deadlineMs`, generation, or base epoch. [VERIFIED: convergence spec; `src/engine/types.ts`]
- Force `Stable -> Recovering` for the valid disband candidate even if its parent is the current tip and there is no sibling. This is a terminalization boundary, not proof of a fork. [VERIFIED: convergence spec]
- Reuse unchanged branch scoring. A disband branch gets no priority. A losing candidate remains a normal losing edge and has no terminal effect. [VERIFIED: convergence and lifecycle specs]
- After frozen-batch resolution, selected active state returns to Stable. A selected disband state transitions Recovering -> Disbanded and can never return to Stable. [VERIFIED: convergence spec]

### Durable terminalization and public effects

- Expose public initiation operations for both legacy enablement and irreversible disband request (recommended surface: `enableDisbanding()` and `disband()`/`requestDisband()`). Public disband initiation must persist one idempotent Pending request **before** Commit preparation, immediately install the non-canonical `Disbanding` outbound gate, and return the same logical request on repeat calls rather than preparing parallel terminal intents. [VERIFIED: `refs/marmot/app-components/group-lifecycle-v1.md`, “Convergence and realization”; `refs/mdk/crates/cgka-engine/src/disband.rs`]
- The pending local request survives publication failure, restart, a losing disband candidate, and `Unrecoverable`; after selection of an active branch, an authorized client regenerates the exact disband Commit against that selected state. Only verified loss of membership or admin authority ends it with a typed local failure. Selection of any valid disband branch satisfies and clears the request, regardless of which admin authored that winning Commit. [VERIFIED: `refs/marmot/app-components/group-lifecycle-v1.md`, “Convergence and realization” and “Authorization failure”; `refs/mdk/crates/cgka-engine/src/disband.rs`]
- Persist a versioned tombstone keyed by group id containing at minimum terminal version, selected epoch, Commit digest/id, and authenticated actor. These are enough to restore status and exactly-once event identity without retaining live MLS secrets. [VERIFIED: lifecycle tombstone requirements; MDK `DisbandTombstone` pattern]
- In one logical persistence boundary: write tombstone, mark terminal notification delivered/pending as appropriate, clear live serialized `ClientState`, clear rewind/candidate/pending ingress/outbound work, and disable routing. If the storage abstraction cannot transact across backends, use an idempotent ordered recovery protocol in which tombstone write is first and cleanup retries on load. [VERIFIED: lifecycle spec; MDK transactional ordering; existing stores are independently injected]
- Expose terminal status from tombstone lookup, not from a synthetic mutable MLS state. Recommended names: `MarmotGroupStatus = "active" | "removed" | "disbanded"`, `MarmotGroupEvents.disbanded(actor, commitDigest)`, and `GroupsManagerEvents.disbanded(groupId, actor, commitDigest)`. [VERIFIED: established event/type conventions; naming is agent discretion]
- Emit exactly one actor-attributed disband event only after durable tombstone establishment. Suppress epoch/member/admin/component presentation rows for the terminal Commit; the spec specifically forbids removal rows for the same Commit. [VERIFIED: lifecycle spec; inbound-processing spec]
- Recommended typed outbound result is a discriminated terminal error/result such as `{ kind: "terminal", reason: "group_disbanded" }`, shared by app message, Commit, maintenance, and queued-drain seams. If existing public APIs throw, use an exported `GroupTerminalError` carrying `reason: "group_disbanded"`; do not expose only message-text matching. [VERIFIED: D-03; project discriminated-union convention]
- Classify all later inbound as stale/inactive before decrypt or convergence. Reusing `stale_epoch` is protocol-compatible with current SelfEvicted handling, but a terminal-specific internal/public reason `group_disbanded` is preferable for observability while mapping to the same stale disposition family. [VERIFIED: D-04; `src/core/inbound.ts`; MDK maps tombstone traffic to ignored/unknown-group after permanent dedup]

### Pattern 1: Pure Commit Classification, Seam-Specific Disposition

**What:** Keep protocol legality independent of storage, scheduler, and transport. All send, inbound, and replay/convergence paths call the same predicate, then choose their local error/disposition. [VERIFIED: `src/core/components/integrity.ts` established pattern]

```typescript

export type DisbandClassification =
  | { kind: "notDisband" }
  | { kind: "validDisband"; actor: string }
  | { kind: "invalidDisband"; reason: DisbandViolationReason };
```

### Pattern 2: Tombstone-First Idempotent Cleanup

**What:** The tombstone is the authority. Once written, every load/ingress/send path treats the group as terminal even if cleanup was interrupted. Cleanup of live state, history, pending ingress, timers, and routing is repeatable. [VERIFIED: lifecycle durability requirement; MDK restoration/cleanup pattern]

### Pattern 3: Candidate Metadata, Not Early State Mutation

**What:** Persist `disbands: true` and actor/digest alongside candidate/history evidence. Do not set public status or mutate the canonical state when the candidate merely arrives. [VERIFIED: D-07; MDK `record_inbound_disband_candidate`]

### Anti-Patterns to Avoid

- **Treating disband as ordinary linear Commit:** it bypasses competing input and violates the mandatory selection boundary. [VERIFIED: convergence spec]
- **Adding “disband wins” to branch comparison:** terminal candidates have no score preference. [VERIFIED: convergence spec]
- **Encoding terminality only in `ClientState`:** cleanup must delete live MLS state, so restart would lose the terminal fact. [VERIFIED: lifecycle spec]
- **Emitting member removals plus disband:** creates forbidden duplicate presentation semantics. [VERIFIED: lifecycle spec]
- **Using the removed marker unchanged:** removal can be withdrawn during convergence; selected disband cannot. Keep storage/event identities distinct. [VERIFIED: `src/client/session/group-session.ts`; lifecycle spec]
- **Canceling durable local request on publish failure, losing branch, or Unrecoverable:** only loss of membership/admin authority produces typed failure; transport and repairable state leave it pending. [VERIFIED: lifecycle spec; MDK disband workflow]

## Common Pitfalls

### Pitfall 1: Validating against the current tip rather than candidate parent

**What goes wrong:** a valid fork candidate is rejected or an unauthorized one is accepted. **How to avoid:** derive committer/admin/leaf facts from the exact retained parent on which MLS authentication succeeds. **Warning sign:** validator arguments contain only `this.state`. [VERIFIED: convergence spec]

### Pitfall 2: Missing same-account sibling leaves

**What goes wrong:** the final state retains another leaf owned by the committer account. **How to avoid:** compare leaf indices, retaining only the exact committing leaf. **Warning sign:** removals are deduplicated by account identity. [VERIFIED: lifecycle spec]

### Pitfall 3: Restart resurrection

**What goes wrong:** live state cleanup succeeds but terminal metadata was never saved, or legacy loader ignores it. **How to avoid:** tombstone-first idempotent cleanup and load-time terminal restoration. **Warning sign:** `GroupsManager.load()` requires serialized `ClientState` to expose a disbanded group. [VERIFIED: D-01; MDK restore path]

### Pitfall 4: Early or duplicate event emission

**What goes wrong:** losing candidate emits terminal UI or restart emits twice. **How to avoid:** key terminal effect by selected Commit digest and persist delivery evidence before/with emission. **Warning sign:** event fires in ingest validation rather than canonical apply/reconcile. [VERIFIED: D-02/D-07; existing notification ledger pattern]

### Pitfall 5: Timer/base mutation on forced recovery

**What goes wrong:** late disband input extends the pass or changes candidate eligibility. **How to avoid:** reuse the existing pass object; only open once and preserve deadline/base/generation. **Warning sign:** forced recovery calls a generic “reset pass” helper. [VERIFIED: D-06; convergence spec]

### Pitfall 6: Cleanup races with direct engine callers

**What goes wrong:** client routing is stopped but direct `engine.send` or queued drains still operate. **How to avoid:** gate at public ingress and authoritative engine mutation boundary; repeat the check in queued-drain paths. [VERIFIED: MDK send gates; current layered API]

## Open Questions

1. **(RESOLVED) Does Phase 04.1 include the full durable local `Disbanding` request/regeneration workflow? — Yes.**
   - Decision: expose public enable/request initiation, persist one idempotent Pending request before preparing any Commit, gate every ordinary outbound and queued-drain path immediately, regenerate against a selected active winner, retain the request through publication failure/restart/losing branches/repairable or Unrecoverable pauses, and terminate it before disband only for typed `no_longer_member` or `no_longer_admin` authority loss. A selected valid disband branch clears it regardless of author. [VERIFIED: `refs/marmot/app-components/group-lifecycle-v1.md`, “Convergence and realization” and “Authorization failure”; `refs/mdk/crates/cgka-engine/src/disband.rs`]

2. **(RESOLVED) How are tombstone and live-state cleanup made restart-safe across independently supplied stores? — Tombstone-first, idempotent cleanup.**
   - Decision: the successful durable tombstone write is the terminal commit point. Every load/send/ingest path consults it before stale live bytes; deletion of live ClientState, rewind/candidates, request, pending ingress/outbound work, routes, and timers is repeatable and resumes on load after interruption. Ordinary cleanup must not remove the tombstone; only an explicitly documented irreversible local purge may do so. This preserves D-01 without pretending the existing independently injected stores share a transaction. [VERIFIED: `src/client/session/group-session.ts`; client option types; `refs/marmot/protocol-core/durability.md`; MDK tombstone restoration pattern]

3. **(RESOLVED) Should new groups require lifecycle-v1 immediately? — Yes.**
   - Decision: new groups carry active lifecycle state and require `0x800c`; the omission exemption applies only to predating groups. A legacy enablement Commit is accepted only if every resulting leaf advertises `0x800c`. [VERIFIED: `refs/marmot/app-components/group-lifecycle-v1.md`]
