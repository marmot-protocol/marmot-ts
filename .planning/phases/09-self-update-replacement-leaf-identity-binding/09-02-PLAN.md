**A. `src/core/components/integrity.ts`.**

Export `type CommitLegalityOutcome` as a three-member discriminated union on `kind`: `{ kind: "legal" }`,
`{ kind: "violation"; violation: CommitIntegrityViolation }`, and `{ kind: "undecidable"; detail: string }`. Document
that `violation` is terminal (the seam rejects, throws, or drops the edge per its own convention) while `undecidable`
means authorization could not be evaluated against this candidate parent and MUST map to the seam's deferral idiom,
citing `refs/marmot/foundation/errors.md` lines 63-68. `detail` is a pubkey-free diagnostic string. Leave
`CommitIntegrityViolation` and `CommitIntegrityViolationReason` exactly as they are — D-06 adds no fields.

Change `validateCommitAccountIdentityProofs` to return `CommitLegalityOutcome` and to accept an optional third
argument property `classification?: ChangedLeafClassificationInput`. Keep both existing profile-drift checks
unchanged in behavior and order, wrapping their returns as `{ kind: "violation", violation: ... }`.

Restructure the changed-leaf loop as follows. Track a local `undecidableDetail: string | undefined`, initially unset.
For each entry of `diffChangedLeaves(...)`:
1. Run `validateLeafAccountIdentityProof(entry.leaf, args.resultingState.groupContext.cipherSuite)` in try/catch
   exactly as today, returning the same violation shape on throw. This ordering is load-bearing: proof validity is
   checked before classification, so UPD-02 and UPD-03 keep reporting their existing proof reasons regardless of
   which bucket the leaf falls into.
2. Call `classifyChangedLeaf(entry, args.classification)` and switch on the result:
   - `add`: continue. A new member in a freed slot legitimately carries a different identity, so no prior-identity
     comparison runs (D-01).
   - `update-proposal` or `committer-update-path`: enforce identity equality (UPD-01). If `entry.parentLeaf` is
     `undefined`, the slot had no prior occupant, which is impossible for a genuine replacement — return a violation
     with `proofReason: "unattributable-leaf"` and `leafIndex`. Otherwise compare
     `getCredentialPubkey(entry.leaf.credential)` against `getCredentialPubkey(entry.parentLeaf.credential)` inside
     try/catch; a throw from either call yields a violation with `proofReason: "invalid-credential"` and `leafIndex`.
     When the two differ, return `{ kind: "violation", violation: { reason: "account-identity-proof", detail:
     "member leaf <leafIndex> replacement leaf changed account identity", proofReason: "member-identity-changed",
     leafIndex } }`.
   - `unattributable`: return a violation with `proofReason: "unattributable-leaf"`, `leafIndex`, and a detail naming
     the leaf index only (D-02 fail closed).
   - `undecidable`: do NOT return yet. Record `undecidableDetail` (naming the leaf index only) if not already set, and
     continue to the next leaf.
3. After the loop, return `{ kind: "undecidable", detail: undecidableDetail }` if it was set, otherwise
   `{ kind: "legal" }`.

The deferred-last ordering is required: a definite violation anywhere in the commit must outrank an undecidable leaf,
otherwise a provably illegal commit would be pooled and retried until it ages out instead of being rejected.

the phase to leak a pubkey (D-06, `refs/marmot/foundation/errors.md` lines 122-125). Update the function's doc comment
to describe the three buckets, the fail-closed and deferred branches, and to replace the now-incorrect D-03 sentence
stating that no prior-leaf identity comparison is performed.
