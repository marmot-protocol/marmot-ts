  commit. The digest still enters the ledger, so a later rewind can reach and withdraw the entry;

  current `continue` skips `record()` and leaves that link permanently non-withdrawable (the CR-07

  `Unrecoverable` — far too large a blast radius for a non-protocol concern on already-persisted
  state.
- **D-12 (LOCKED):** **A failing-first regression test per finding, no exceptions.** Every fix

## Summary

The current phase is a narrow four-finding closure, not the older 30-finding program described when `03.1-CONTEXT.md` was gathered. The latest review supersedes those stale counts and identifies CR-01, CR-02, CR-03, and WR-01. [VERIFIED: current `03-REVIEW.md`] All four are boundary-ordering defects: state or a marker becomes canonical before the corresponding consumer observation is safely surfaced. [VERIFIED: codebase grep]

The clean plan is three implementation slices after a mandatory reference update: (1) make removal hydration listener-safe and concurrent realization single-flight; (2) define one notification-bearing post-confirm result that can also report ancillary save/Welcome failures without erasing confirmation; (3) route auto-commit through that result and yield its applied notifications before any future withdrawal can appear. [VERIFIED: codebase call-chain inspection] The existing engine ledger and digest attribution are already correct; the defects are above the engine, mainly in `GroupRegistry`, `MarmotGroup`, and `GroupRuntime`. [VERIFIED: `group-engine.ts`, `group-registry.ts`, `marmot-group.ts`, `group-runtime.ts`]

**Primary recommendation:** Treat canonical confirmation as the irreversible semantic boundary: after `confirmPublished`, always return a typed confirmed result with notifications; report later save/Welcome failures as ancillary outcomes, never by rejecting as though the commit did not apply. [VERIFIED: upstream Marmot commit `4a2bc65` and current review CR-03]

### Pattern 1: Irreversible confirmation boundary

**What:** Split failure handling into pre-confirm failures, which reject and roll back pending state, and post-confirm ancillary failures, which must return confirmation plus notifications and a typed failure status. [VERIFIED: current review CR-03; upstream `refs/marmot` commit `4a2bc65`]

**When to use:** Both self-update and group-evolution commit paths; proposal behavior can remain unchanged because it derives no state notifications. [VERIFIED: `group-runtime.ts`]

```typescript
// Shape is illustrative; exact names remain planner discretion.
type ConfirmedCommitResult = {
  response: Record<string, PublishResponse>;
  notifications: StateNotification[];
  persistence: { kind: "saved" } | { kind: "failed"; error: unknown };
  welcomeDelivery?: { kind: "delivered" } | { kind: "failed"; error: unknown };
};
```

### Pattern 2: Single-flight idempotent realization

**What:** Cache the in-flight Promise before the first await; all concurrent callers await it. Clear it on failure so a later call retries. Keep the durable marker as restart idempotency and the Promise as same-instance concurrency idempotency. [VERIFIED: current review WR-01]

### Pattern 3: Attach listeners before state-derived effects

**What:** `load()` hydrates only; `get()`/manager adoption tracks the instance, then triggers reconvergence and realization, then emits `loaded`. If an API must return only after reconvergence, put the ordering in one registry orchestration method rather than letting callers compose it inconsistently. [VERIFIED: current CR-01 call chain]

### Anti-Patterns to Avoid

- **Rejecting after confirmation:** hides already-ledgered notifications and encourages unsafe retry. [VERIFIED: CR-03]
- **Returning only relay responses from commit helpers:** loses notification metadata at alternate call sites such as auto-commit. [VERIFIED: CR-02]
- **Appending notifications to the original `autoCommit` result ad hoc:** the locked context requires the same consumer-facing applied-notification shape used elsewhere. [VERIFIED: `03.1-CONTEXT.md`]
- **Mutex via runtime-specific primitives:** breaks cross-runtime compatibility; one cached Promise is sufficient. [VERIFIED: project constraints]
- **Reordering only `GroupRegistry.get` while leaving manager adoption/load paths separate:** recreates CR-01 at another construction seam. [VERIFIED: context and registry call-chain inspection]

## Common Pitfalls

### Pitfall 1: Swallowed auto-commit failure conflates pre- and post-confirm errors
**What goes wrong:** The existing blanket `catch {}` is correct only for publish failure that rolled pending state back. A post-confirm save/Welcome failure cannot be swallowed as if the auto-commit were retryable. [VERIFIED: `marmot-group.ts`, CR-03]
**How to avoid:** Give runtime results a committed discriminator; retry only pre-confirm failures. Test that canonical epoch advances once and a second intent is not published. [VERIFIED: review recommendation]

### Pitfall 2: `get()` dedup does not make a public method idempotent
**What goes wrong:** Two explicit calls to `realizeRemovalIfNeeded()` can overlap their store reads and emit twice. [VERIFIED: WR-01]
**How to avoid:** Force overlap with a deferred `getItem` test, call via `Promise.all`, and assert one get/set/event sequence. [VERIFIED: codebase testing pattern]

### Pitfall 3: Testing a removed tip without a competing tree misses CR-01
**What goes wrong:** The post-track realization test passes, but `load()` reconvergence consumes the marker first only when the tree has multiple tips. [VERIFIED: CR-01]
**How to avoid:** Persist an actual multi-tip `GroupHistoryTree`, load through `GroupsManager`/registry, and assert exactly one manager-level `removed` plus marker. [VERIFIED: review fix]

### Pitfall 4: Delivering a withdrawal for an unseen application
**What goes wrong:** Auto-commit confirms and records notifications, but ingest yields only `autoCommit`; later rewind yields `stateInvalidated`. [VERIFIED: CR-02]
**How to avoid:** Regression must record delivered commit digests and assert every withdrawn digest was previously delivered. [VERIFIED: review fix]

### Pitfall 5: Reference drift changes the correct solution
**What goes wrong:** Local `refs/marmot` is one relevant commit behind and `refs/mdk` is far behind; planning solely from pinned source misses the new durability contract and recent MDK implementation patterns. [VERIFIED: `git fetch`/`log`]
**How to avoid:** First plan task fast-forwards both submodules, reviews relevant diffs, and commits only pointer bumps. [VERIFIED: `AGENTS.md`]
