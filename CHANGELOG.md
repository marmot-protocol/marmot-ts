# @internet-privacy/marmot-ts

## Unreleased

### Added

- Reuse one persisted leaf signature key per installation across KeyPackages with the new `getSignatureKeyPair` option on `MarmotClient` (or `signatureKeyPair` on `generateKeyPackage`). Other clients can then match a member's leaf to its published KeyPackages after the one used to join was consumed, as they can for MDK devices. Init and encryption keys stay fresh for every KeyPackage.

### Fixed

- Groups created before 0.7.0, with the app-data dictionary first in their GroupContext extensions, can now be renamed and have their admins, relays or other components changed without splitting off White Noise members. The first such commit by a marmot-ts admin also moves the dictionary last, so later updates need no repair. Groups that already split on an earlier update are not recovered.
- Refuse to invite (or found a group with) a KeyPackage whose leaf does not advertise every app component the group requires, or a required agent-text-stream role. MDK members reject such an Add commit, so the group forked: marmot-ts members moved to the next epoch and White Noise members did not. `evaluateKeyPackageForGroup()` now reports missing app components too, and the check is exported as `missingGroupRequirements()`.
- Application messages are decoded as strictly as MDK: payloads with a duplicate member, an uppercase `id` or `pubkey`, a `created_at` or `kind` that is not a plain non-negative integer (`1.5`, `1.0`, `1e9`, `-1`), an unpaired surrogate, invalid UTF-8 or a leading BOM are now rejected. White Noise already dropped these, so a member could show marmot-ts users messages White Noise users never saw.
- An admin removed by another admin now accepts its removal and sees the group as left. Previously its client rejected the removal commit as an `admin-leaf-coupling` violation and kept presenting the group as active.
- Every commit's complete resulting state is checked against the current Marmot profile, as MDK does: every member leaf must advertise the group's required MLS capabilities and app components, the group must keep requiring the app-data dictionary, admin policy and account proof, every required component must be known and have state, and the frozen encrypted-media v1 component (`0x8008`) is not allowed. Previously marmot-ts applied commits White Noise rejects, such as adding a KeyPackage without a required component, and the group split. marmot-ts now also refuses to create such commits, including encrypted-media v1 updates.
- Competing commits in the same epoch are ranked the way MDK and the spec rank them: an admin's commit (rename, invite, removal, admin change) beats a self-update or SelfRemove-only commit before the committer and digest tie-breakers. Previously marmot-ts could keep a different branch than White Noise members, splitting the group, and the history re-scoring pass could undo the branch fork recovery had just chosen. Removal recovery ranks the removing commit the same way.
- Every proposal is authorized against its own sender, as MDK does: in v1 a non-admin may only send SelfRemove, and an admin may not send SelfRemove until it has left the admin set; PreSharedKey, ReInit, ExternalInit and unknown custom proposals are refused. Previously marmot-ts staged any member's standalone rename, removal or other admin-only proposal, and an admin's next commit carried it by reference; White Noise members rejected that commit and the group split. Local `send({ kind: "proposal" })` now throws `ProposalAuthorizationError` instead of publishing a proposal every peer refuses.
- A staged proposal from the group's first member no longer loses its sender when group state is saved or copied (fixed in the bundled MLS fork).
- KeyPackages generated by `MarmotClient` now use the client's `cryptoProvider` instead of the default provider.
- KeyPackages generated by `MarmotClient` now advertise the client's `capabilities` option, which was previously ignored. Marmot's required capabilities are always included.
- Inviting from a kind 30443 event now checks that its tags describe the KeyPackage it carries, as MDK does: the `i` tag must be the KeyPackageRef, and `mls_ciphersuite`, `mls_extensions`, `mls_proposals` and `app_components` must each appear once and match the decoded LeafNode (`mls_proposals` with the same GREASE rules as `checkKeyPackageProposalsTag`). White Noise already rejected these events, so marmot-ts could invite from a KeyPackage other clients ignore. The check is exported as `validateKeyPackageEventMetadata` and throws `KeyPackageEventMetadataError`.

### Changed

- `GroupsManager.connect()` and `connectAll()` fetch a group's kind 445 backlog in pages and, after a relay's first complete backfill, only from that relay's cursor (minus a slack window); the live subscription starts a slack window before the backfill. Cursors are stored in `ingestStateStore`, so pass a durable one to keep reconnects cheap across restarts. A relay that fails or stays incomplete re-reads its own window on the next connect without holding back the others, and a backfill that hits the page cap resumes below the range already read. A cursor does not advance past events the group still holds only in memory (unless they are dated more than seven days before the newest event), or when a relay answers outside the requested window or may have truncated a one-second page. Tune with the new `backfillSlackSeconds`, `backfillPageSize`, and `backfillMaxPages` connect options. The network adapter's `request` must reject when a relay fails or times out.
- `serializeApplicationRumor` writes only the six Marmot app-event members (a `sig` or other extra field is no longer sent) and throws instead of producing a payload that receivers would drop.

### Breaking changes

- `groups.leave()` by an active admin now throws before publishing or deleting anything. Previously it published a SelfRemove that every peer rejected and then destroyed the local group, leaving the admin in the group for everyone else. To leave, first remove yourself from the admin set (another admin must remain), then call `leave()`.

## 0.7.0

### Added

- Follow the dedicated [Group images guide](docs/client/group-images.md) for explicit Blossom configuration, verified reads, cancellation, replacement and snapshot-safe display.
- Clear encrypted Blossom image metadata while preserving URL avatars. Clear leaves remote blobs and previously shared upload credentials intact; remote deletion and credential revocation require application/service policy.
- Replace and clear encrypted group images through the normal MLS confirmation workflow, and retrieve verified image bytes through `MarmotGroup.image` using explicit application endpoints.
- Encode, encrypt and authenticate encrypted Blossom group-image metadata through pure core helpers, with independent image credentials and ciphertext integrity checks.
- Read a canonical group image source that preserves URL-avatar precedence and identifies complete Blossom metadata snapshots without downloading image bytes.
- Import `marmotAuthService` from the root or `/core` entrypoint for MLS basic-credential identity and curve validation. Account-proof binding and group authorization remain separate Marmot checks.
- Use `MarmotGroupEngine` from the engine entrypoint to manage group state without a Nostr transport, with changes applied after successful publication.
- Use `GroupSession`, `MarmotGroup.session`, and `MarmotGroup.runtime` for direct control over group send, receive, persistence, and publication. `GroupsManager` adds session and runtime helpers, including Welcome delivery.
- Encrypt and decrypt group media with `GroupMediaService`, including a cache for decrypted media.
- Enable optional forensic audit logging to investigate group activity.
- Check group compatibility through `profileSupport` and identify older KeyPackages through `ListedKeyPackage.nonCurrent`.
- Receive account identity proof rejection details and group removal or disband notifications during recovery.

### Changed

- Packed installations validate all ten supported code entrypoints using isolated production consumers, including NodeNext and bundler type imports. The default MLS ciphersuite works without any of the five optional cryptographic backends or an upstream `ts-mls` installation; install an optional backend only when selecting its ciphersuite. Import the bundled fork through `/mls`. Strict consumer checks use `skipLibCheck: true` and do not promise dependency-wide declaration validation.

- Named public signature types improve typed consumers and API reference coverage; `pnpm typecheck:tests` now checks every source test and helper independently of runtime tests. For publisher options, import `GenerateKeyPackageOptions` from `@internet-privacy/marmot-ts/client`; root and `/core` imports retain the existing core generator type. These exports are type-only, with unchanged runtime exports. See [Client](docs/client/marmot-client.md#key-package-management) and [Storage upgrades](docs/client/storage.md#upgrading-existing-stores) for import and checkpoint guidance.

- Release publication dependencies after conclusive rollback, confirmation, or rejected preparation before effects reach a publisher, including cancelled Commits and leave proposals. Finite recovery retention can then contract; returned application work and retryable publication failures keep their source pinned until acknowledgement.

- Keep lifecycle enablement admitted through asynchronous MLS preparation and wrapping, preventing settled retention from interrupting an in-flight enablement send.

- Preserve staged resumption-PSK receivers on every selectable recovery source, so valid competing Commits remain replayable after retention and restart. Receivers are released once their source and unfinished dependencies expire.

- Expired application messages remain stale when their source snapshot is retained for recovery, including explicit `Infinity`, even after the separate application receiver window releases old keys. Authentication uses an independent retained copy and preserves live ratchets.

- Long-lived groups using the default finite window now release obsolete recovery snapshots, duplicate identities, completed delivery evidence and private plaintext cache copies after convergence settles, while preserving eligible forks and unfinished recovery, publication and retraction work. Pending work can temporarily exceed the horizon; explicit `Infinity` keeps historical recovery material without widening the application decryption window. Application rumor history and custom media remain application-controlled.

- Existing generic stores are read by the updated loader and upgraded through checkpoint/evidence metadata with restartable exact-key cleanup. Preserve the recovery and ingestion stores together, keep single-value writes atomic and coordinate separate writers; no key renaming or store clearing is required. After a version-2 tree checkpoint is saved, use the updated loader rather than downgrading to an older one. See [Storage](docs/client/storage.md#retention-checkpoint-and-restart-repair) for adapter requirements and migration limits.

- Cancelling an image replacement or closing its image service now stops queued and preparing MLS image changes before publication, while ordinary group operations remain usable. Image changes already being published retain their publication outcome.

- Keep verified image bytes intact when a cache entry is replaced or evicted while a read is awaiting contact policy; cancelled and closed reads release their private plaintext.

- Group destruction now waits for admitted lifecycle storage writes and refuses stale disband, lifecycle enablement, leave, and publication work, preventing deleted groups from recreating local data or publishing a terminal commit after closure.

- Group image replacements and clears share a bounded FIFO queue tied to the loaded group instance. Unloading or destroying a group closes its image service and prevents queued changes from reaching a replacement instance.

- Encrypted group-image reads share work only across compatible caller profiles, keep cancellation independent, and cache verified plaintext in bounded memory. Cached and shared results recheck current policy and canonical image metadata before delivery.

- Encrypted group-image HTTP operations reject redirects and malformed upload descriptors, enforce streaming byte and time limits, and use narrowly scoped image credentials with explicit contact policy checks.

- New KeyPackages advertise encrypted group-image support. Recovery validates image metadata and parent-admin authority, and authorized commits can atomically unrequire and remove optional image metadata.

- Direct session/facade commits that change encrypted group images now require `expectedParent: group.session.parentToken`, captured before upload or other asynchronous preparation. Stale replacements are refused after convergence waits; ordinary commits keep the existing contract.

- Application messages include an exact NIP-40 expiration hint computed with checked bigint arithmetic from the inner timestamp and source epoch's retention policy. Missing or disabled retention, invalid timestamps and overflowing sums omit the hint; commits and proposals remain untagged. Retries preserve the original signed event even after policy changes.
- Fork invalidations include strict rumor and transport IDs plus the losing state's producing commit when known. Delivered evidence survives restarts when both ingestion-state and rewind stores are persisted; older messages without ledger evidence remain unattributable.
- Bundle the forked MLS implementation with the library. Import MLS primitives from `@internet-privacy/marmot-ts/mls`; additional cryptographic backends are optional dependencies needed only for their ciphersuites.
- Sign account identity proofs with the client's own signer using the current `0x8009` member proof format.

### Fixed

- Reject `app_components` lists whose ids are not in ascending order, matching MDK, so marmot-ts and White Noise members agree on which GroupContexts, LeafNodes and KeyPackages are valid.
- Enforce the spec's 16-relay limit on Nostr routing state when encoding and decoding. Larger relay lists made Welcomes unjoinable and routing updates fail for White Noise members. The limit is exported as `NOSTR_ROUTING_MAX_RELAYS`.
- Group avatar URLs on localhost or private-network hosts are now valid group state, as the spec requires and MDK accepts. Previously marmot-ts members rejected a White Noise commit setting such an avatar and fell an epoch behind. Call the new `rejectUnsafeGroupAvatarContactUrl()` before fetching or rendering an avatar.
- Reject URLs ending in an empty fragment (a trailing `#`) in avatar URLs, encrypted-media endpoints and Nostr routing relays, as MDK does. A group created with such an avatar could not be joined by White Noise users.
- Messages and commits sent while a group is settling after a commit are now always published once the group settles, even when the settle timer fires slightly early or retained messages are processed at the same time. Previously such sends could stay pending indefinitely.
- New groups keep the app-data dictionary last in their GroupContext extensions, matching MDK, so renames, admin changes and relay updates no longer split White Noise members off the group. Existing dictionary-first groups are not migrated yet.
- Application messages are no longer lost when they are read up to five commits after being sent, or while catching up on a burst of more than ten messages. MLS key retention now matches the spec and MDK: 5 past epochs, 100 skipped generations and a 1000-step forward limit.
- A member's message read after the commit that removed them is now delivered instead of dropped as `invalid-app-payload`. This mostly affected a member's last message before leaving, which often arrives in the same batch as their removal.
- `GroupsManager` now drops kind-445 events carrying tags other than the single `h` tag and at most one NIP-40 `expiration` tag, reporting them as `tag-cardinality` rejections. MDK drops these before decryption, so a member could otherwise show marmot-ts users messages White Noise users never see.

- Removal recovery uses the authenticated committer tie-breaker for retained branches and removal evidence, matching normal fork selection. Older removal records remain conservative when their committer identity is unavailable.

- Restored groups can decrypt media from intermediate epochs on their recovered canonical branch immediately, using the existing bounded retained-key window.

- Disband cleanup waits for already-started history writes before purging plaintext, so overlapping sends cannot recreate deleted history after terminal selection.

- Recover removed membership only through an authenticated winning retained branch, keeping sends blocked until durable recovery completes. Canonical disband now fences sends immediately and repairs interrupted terminal persistence after restart without deleting unfinished effects or history retractions in shared stores. Configure durable lifecycle, removal-marker, ingestion and rewind stores for restart recovery; callback attempts can still be lost around a crash.

- Concurrent founding Welcome retries for the same recipient share one delivery while other recipients proceed independently. Successful outcomes remain successful without redelivery even when a concurrent founding fanout later fails; failed attempts permit a later explicit retry. Changed Welcomes, authors or recipient KeyPackages start independent delivery obligations, protected from older attempts.
- Founding Add preparation refuses with a clear retryable error after engine-mediated state or lifecycle mutation history, or a proposal edit still present after proposal resolution or real commit construction, before staging or adopting output. Refusal preserves intervening canonical and pending work. `ClientState` remains caller-mutable: direct nested proposal edits fully restored before both checkpoints are outside the guarantee; do not mutate returned state during an in-flight founding operation.

- Classify public and private MLS commits and proposals correctly, and sort mixed-carriage commits by their actual source epoch and canonical MLS-message digest without changing the input array. Ordering now explicitly rejects unsupported wire formats and negative or unsafe epochs.

- Reject malformed encrypted group-image metadata in Welcome invitations before saving a group or consuming its single-use KeyPackage, including optional image components. Valid present and cleared images remain supported.

- Closing a group-image service also cancels active uploads and queued image changes, wipes owned plaintext buffers, and prevents late callbacks from delivering an image after closure.
- Unloaded sessions refuse delayed storage writes and notifications; publication results refuse late Welcome completion after the owning group closes.

- Image changes recheck current admin membership, profile, canonical parent and lifecycle after uploads and during MLS preparation. Closed groups abort image uploads and refuse late publication or persistence completion.

- Refuse encrypted group-image proposals, clears and removals from non-admin members, prevent an admin commit from accepting a referenced image proposal authored by a non-admin, and reject malformed image metadata carried forward by a commit.

- Destroying or successfully leaving a group deletes its plaintext delivery ledger and pending retractions, and fences delayed saves so cleanup cannot recreate them.
- Keep canonical history rumors visible when another transport delivery of the same rumor loses convergence, including restored pending retractions.
- Preserve every losing-branch history retraction across interrupted multi-message rewinds and retry outstanding removals after restart.
- Preserve write-ahead terminal convergence evidence before saving rewind history, so interrupted history writes remain recoverable after restart.
- Losing-branch rumors are durably retracted from supported history and live timelines refresh from filtered snapshots, including limited-page refill.
- Group watches accept an `AbortSignal`, finish promptly when cancelled or returned while idle or loading, and retain updates racing with snapshots.
- Serialize connected group ingestion across backfill and live subscriptions, drain admitted work after disconnect, and forward live and timer-driven convergence results through `groups.on("ingestResult", ...)`. Connection options now accept an `AbortSignal` to cancel pending backfill.
- Accept proposal builders returning one or several proposals for ordinary commits and founding Adds, preserving their order and rejecting invalid results before publication.
- Authenticate the real Welcome author and require active admin membership in a fully validated group before saving it. Rejected and duplicate invitations preserve existing group state and KeyPackage material.
- Retire single-use KeyPackage private material after validated durable group adoption, retaining public metadata for rotation and purge. Receipts finish interrupted cleanup after restart or `keyPackages.finalizeConsumptions()`; reusable packages retain their keys for later joins and use the canonical empty-data component marker.
- Publish KeyPackage proposal tags that match the advertised proposals, including GREASE values, so MDK accepts them. Reject missing, malformed, or mismatched proposal tags when selecting invite candidates; matching older tags without GREASE remain supported.
- Validate member identity proofs during sends, ingestion, and fork recovery, preventing invalid membership changes from being accepted.
- Authorize commits against their parent state, including during fork recovery and when an admin is demoted earlier in an ingestion batch.
- Keep admin restrictions enforced when optional group metadata is malformed, and reject invalid group component updates before applying them.

### Breaking changes

- `createGroup` now throws `InvalidGroupContextExtensionError` for a caller-supplied `app_data_dictionary` extension or duplicate extension types, including a second `required_capabilities`. Put dictionary data in `components` and pass at most one extension of each type in `extensions`.

- Successful `isCommitMessage` and `isProposalMessage` guards now narrow to a public/private union. Consumers that read `privateMessage` directly after a guard must branch on `message.wireformat`: use `publicMessage.content` for `mls_public_message` and `privateMessage` for `mls_private_message`. `isApplicationMessage` remains private-only.

- Reusable KeyPackages require the canonical empty-data `0x0004` component in the KeyPackage dictionary; legacy-only `0x000a` markers are deliberately rejected. Generate and republish current packages. Publications omit relay tags; destinations are retained locally across restarts for rotation and purge. Older route-less records need explicit rotation routes or locally supplied tracking routes for cleanup.
- Publication identifiers (`clientId`, `identifier`, and rotation `d`) must be exactly 64 lowercase hex characters and invalid values reject before side effects. Generate 32 random bytes once, encode as lowercase hex and persist that slot instead of a device label. Publish under the new slot, then delete the old publication through known routes: a different `d` does not replace the old address. See the [publication slot migration](docs/core/key-packages.md#publication-slot-migration) for the create/purge and rotation paths.
- Custom `GroupSessionHistory`/`BaseGroupHistory` implementations must implement idempotent `removeMessage(rumorId)`; custom `GroupRumorHistoryBackend` implementations must implement durable `removeRumor(rumorId)`. Remove by the canonical inner ID and resolve only after persistence succeeds.
- Legacy account identity proofs (`0xf2f1`) and their helper exports are removed. New groups require `0x8009`; incompatible groups cannot be joined, and stored incompatible groups refuse traffic. Republish current KeyPackages and explicitly purge obsolete ones. See the [account identity proof migration guide](docs/client/best-practices.md#migrating-to-account-identity-proof-v2-0x8009).
- Separate proof-signer options are removed. `generateKeyPackage` requires a `signer`, and `makeLeafAppComponentsExtension` requires an encoded current proof.
- `ForkRecovery.resolveFork` now takes an `adminCallbackFor` function instead of a single `adminCallback`.
- Ingest results add `unsupported-profile` and `account-identity-proof` reasons. A `rejected` result can now describe a standalone proposal as well as a commit; update exhaustive result handlers accordingly.
