## Critical Issues

### CR-01: Stopping iteration at `autoCommit` strands the engine in `PendingPublish`

**Classification:** BLOCKER  
**File:** `src/client/group/marmot-group.ts:797-825`  
**Issue:** The generator yields the `autoCommit` result before it calls `runtime.publishEffects`. An async generator is suspended at `yield`; if a caller reads one result and returns, breaks, or calls `return()`, lines 799-825 never execute. The locally staged commit is then neither published nor rolled back, leaving the engine in `PendingPublish` and preventing later local commits. This is a regression in the CR-02 closure: the previous implementation published before yielding. Every current test drains the generator, so the cancellation case passes unnoticed.

**Fix:** Complete the publish attempt before the first yield, retain the two-result ordering by storing both results, then yield `autoCommit` followed by `appliedNotifications`. On publication failure, rollback already occurs and only the `autoCommit` result should be yielded (or expose a typed failure result). Add a regression that calls `iterator.next()` once and then `iterator.return()`, and assert the lifecycle is terminal rather than `PendingPublish`.

### CR-02: Failed activation leaves a group cached and permanently bypasses activation retry

**Classification:** BLOCKER  
**File:** `src/client/group-registry.ts:257-275`  
**Issue:** `track()` inserts the group and attaches listeners before awaiting `reconverge()` and `realizeRemovalIfNeeded()`. If either operation rejects (for example, state persistence or removed-marker storage fails), `get()` rejects, but the group remains in `#groups`. The next `get()` takes the cache hit at line 318 and returns that partially activated group without retrying reconvergence, removal realization, or the `loaded` event. Thus the CR-01 listener-before-realization fix exchanges a lost-event race for a permanent failed-activation cache state.

**Fix:** Make activation state explicit. On activation failure, detach the listeners, remove the exact instance from `#groups`/`#groupListeners`, dispose it, and allow the next `get()` to load and retry. Alternatively cache an activation promise/state and require all cache hits to await it. Add rejection-and-retry tests for both `reconverge()` and marker-store failure.

### CR-03: A throwing `removed` listener commits the durable marker but loses the removal transaction

**Classification:** BLOCKER  
**File:** `src/client/group/marmot-group.ts:733-748`  
**Issue:** Removal realization writes the durable marker before synchronously emitting `removed`. EventEmitter listener exceptions propagate out of `emit`. The single-flight promise then rejects and is cleared, but the marker remains true; every retry returns at line 737 and never rejects queued outbound or re-emits the public removal signal. This directly violates WR-01's required “clear on rejection so retry is possible” behavior and can also prevent later listeners from observing removal.

**Fix:** Define listener failures as non-transactional and isolate/report them without rejecting realization, or roll back the marker when the remaining realization work fails so a retry can run. Ensure queued outbound is rejected before any user callback. Add a regression with a throwing `removed` listener followed by a second realization attempt and assert the chosen durable/event semantics explicitly.

### CR-04: Proposal publication still rejects after acknowledgement and loses durable staged state

**Classification:** BLOCKER  
**File:** `src/client/runtime/group-runtime.ts:167-177`  
**Issue:** `publishProposal()` acknowledges the proposal on at least one relay, calls `confirmPublished()` (which mutates the local state and tree snapshot), and then awaits `save()`. A save rejection escapes to the caller as if publication failed. The caller can retry an already-published operation, while a restart loses the locally staged proposal needed to resolve a later `ProposalRef`. The new `GroupPublishResult` branch also hard-codes proposal persistence as `succeeded` at lines 104-111, but that result is never returned on this failure, so the typed post-confirm contract does not cover all publish-before-apply work.

**Fix:** Give proposals the same pre-ack/post-ack split as commits: relay failure may reject; after acknowledgement, return a `GroupPublishResult` with `persistence: { kind: "failed", ... }` and `retryPublication: false`. Do not hide the acknowledged outcome. Add a save-rejection regression that verifies the proposal state remains applied, the result forbids republication, and the persistence failure is inspectable.
