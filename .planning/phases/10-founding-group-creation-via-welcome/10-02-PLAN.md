<objective>
Move the Welcome fanout loop out of `GroupRuntime`'s private method onto `NostrWelcomeDelivery.deliverMany()`
(D-07), make it per-recipient and non-throwing (D-06/D-12), reshape `GroupPublishResult.welcomeDelivery`
accordingly, and migrate the single existing test file that encodes the old aggregate contract (R-03).

Purpose: this is the seam that makes FOUND-04's "delivered independently, retryable per invitee" true for
**both** founding create and ordinary invite, with one implementation. It shares no files with plan 10-01, so
both run in wave 1; plan 10-03 consumes `deliverMany` and `WelcomeDeliveryOutcome` from here.
Output: `deliverMany()` plus its outcome type, a new unit-test file for a class that had none, the reshaped
publish-result field, the rewritten runtime fanout, and a deliberately migrated `group-runtime.test.ts`.
</objective>

```typescript
export type WelcomeDeliveryOutcome =
  | { kind: "succeeded"; recipient: WelcomeRecipient; response: Record<string, PublishResponse> }
  | { kind: "failed"; recipient: WelcomeRecipient; error: string };

export type DeliverManyWelcomesOptions = {
  welcome: Welcome; author: string; groupRelays: string[]; recipients: WelcomeRecipient[];

export type WelcomeFanoutOutcome =
  | { kind: "notRequired" }

```

Pinned design decisions for this plan (Claude's Discretion, now fixed — do not re-open):
- The per-recipient element is an array entry carrying its own `recipient`, not a record keyed by pubkey: the
  same pubkey cannot appear twice in a valid recipient list, but array order preserves the caller's ordering
  and matches `Promise.allSettled`'s contract without an intermediate index map.
- `welcomeDelivery` keeps a `{ kind: "notRequired" }` member. Every existing assertion of that exact value (on
  application-message, proposal and self-update results) therefore stays valid and must not be edited — only
  genuinely-changed assertions change (R-03).
