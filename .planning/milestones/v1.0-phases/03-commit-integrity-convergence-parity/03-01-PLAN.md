Create `src/core/components/integrity.ts` with the module header `/** @module @category Core - App Components */`, named exports only, `.js` extensions on every relative import.

Export the shared violation vocabulary first:

- `export type CommitIntegrityViolationReason = "component-integrity" | "admin-leaf-coupling";`
- `export interface CommitIntegrityViolation { reason: CommitIntegrityViolationReason; detail: string }`

Export `export interface AppDataUpdateOp { componentId: AppComponentId; data: Uint8Array | undefined }` where `data === undefined` means a Remove operation (MDK models this as `Option<&[u8]>` with `None` = Remove).

Export `collectAppDataUpdateOps(proposals: readonly Proposal[]): AppDataUpdateOp[]` — the single adapter every seam uses. It filters `proposals` on `proposalType === appDataUpdateProposalType` (import `appDataUpdateProposalType` from `ts-mls`), narrows via the `appDataUpdate` field, and maps `operation === "update"` to `{ componentId, data: update }` and `operation === "remove"` to `{ componentId, data: undefined }`. Preserve commit order; do not deduplicate.

Export `validateAppComponentIntegrity(args: { currentExtensions: GroupContextExtension[]; resultingExtensions: GroupContextExtension[]; appDataUpdateOps: readonly AppDataUpdateOp[]; requiredIds: readonly AppComponentId[] }): CommitIntegrityViolation | undefined`.

Body, in this exact order (ported from the MDK function named above, whose three enforced rules are numbered in its rustdoc):

1. Read both dictionaries with ts-mls `getAppDataDictionary(extensions)` — NOT the typed accessors in `dictionary.ts` — so unknown component ids participate. If the current dictionary is defined and the resulting one is undefined, return a violation with reason `"component-integrity"` and a detail naming the dropped `app_data_dictionary`.
2. Build the protected id set as `new Set(args.requiredIds)` plus `APP_COMPONENTS_COMPONENT_ID`. For each protected id, if it is present in the current dictionary and absent in the resulting one, return a `"component-integrity"` violation whose detail names the id in `0x` hex.
3. Index `args.appDataUpdateOps` into a `Map<AppComponentId, (Uint8Array | undefined)[]>` of allowed resulting values per component id (an id may legally carry more than one op).
4. Take the union of component ids present in the current OR resulting dictionary. For each id, read `before` and `after` data bytes. Skip when they are byte-equal (both undefined also counts as equal; use a local `bytesEqual(a, b)` helper built on `compareBytes` from `./bytes.js` that treats `undefined` on both sides as equal and `undefined` vs defined as unequal). Otherwise the change must be "update-backed": the map entry for that id must contain a candidate byte-equal to `after` (a Remove op, i.e. `undefined`, backs `after === undefined`). If not, return a `"component-integrity"` violation whose detail names the id in `0x` hex and states the change was outside an AppDataUpdate proposal.
5. Return `undefined` when nothing violated.

`requiredIds` MUST be derived by the caller from the CURRENT (pre-commit) extensions — see Pitfall 2; document this constraint in the JSDoc for the parameter. Do not derive it inside the function from `resultingExtensions`.

The module never throws (D-01/D-02 split: seams decide the disposition). Add a JSDoc block above each export with `@see refs/mdk/crates/cgka-engine/src/app_components.rs` naming the ported function and `@see Marmot v2 spec: app-components/README.md`, matching the citation style already used at the top of `src/core/components/admin-policy.ts`.
</action>

Add to `src/core/components/integrity.ts`:

`export function validateAdminLeafCoupling(args: { currentExtensions: GroupContextExtension[]; resultingExtensions: GroupContextExtension[]; resultingMemberAccounts: readonly string[] }): CommitIntegrityViolation | undefined`

`resultingMemberAccounts` is the set of hex account pubkeys that have at least one member leaf in the RESULTING epoch (D-08: account-level, not leaf-level). Callers at each seam derive it from the post-apply state; the validator itself stays pure and MLS-free.

Body, ported from `validate_admin_leaf_coupling_for_staged_commit`:

1. Resolve the resulting admin set as `getAdminPolicy(args.resultingExtensions)`; if that is `undefined`, fall back to `getAdminPolicy(args.currentExtensions)`; if that is also `undefined`, treat it as an empty array. This is the carried-forward fallback the spec requires (Pitfall 3) — the check MUST run on a membership-changing commit that carries no admin-policy bytes.
2. If the resolved admin set is empty, return `undefined` (vacuously satisfied — component bytes cannot encode an empty admin list, so an empty set means the epoch has no admin-policy state at all; MDK documents the same early return and why it is not a bypass).
3. Build `new Set(args.resultingMemberAccounts)` and return a violation with reason `"admin-leaf-coupling"` if ANY resolved admin key is not in that set. The detail names how many admin keys were orphaned; do NOT put a raw pubkey in the detail string (diagnostics-privacy: the reason enum is the protocol-visible signal, per foundation/errors.md).
4. Otherwise return `undefined`.

Wrap the `getAdminPolicy` calls in try/catch: `decodeAdminPolicyV1` throws on malformed bytes, and a commit that installs undecodable admin-policy bytes must be a `"admin-leaf-coupling"` violation, not an exception escaping a pure validator. On a decode failure of the RESULTING bytes, return a violation whose detail states the resulting admin-policy component did not decode.

Do NOT special-case SelfRemove inside this validator — see Pitfall 4. The validator sees the resulting membership; a non-admin's SelfRemove never changes the admin set and therefore passes trivially, and an admin's SelfRemove is already refused earlier by `createAdminCommitPolicyCallback` in `src/engine/admin-policy.ts`. Note this in the JSDoc so a future reader does not add a redundant carve-out.

Then add the ONE shared seam adapter all three seams call, so the argument derivation is written exactly once (this is what MDK's `cgka-engine/CLAUDE.md` means by "mirror every ingest invariant on every inbound seam through the _same_ shared helper" — a guard that exists on one seam only is a documented bug class, mdk#707):

`export function validateCommitLegality(args: { parentState: ClientState; resultingState: ClientState; proposals: readonly Proposal[] }): CommitIntegrityViolation | undefined`

It is still pure — it takes two `ClientState` values and reads them, performs no I/O, and calls nothing from `src/engine` or `src/client`. Body:

1. `const appDataUpdateOps = collectAppDataUpdateOps(args.proposals)`
2. `const requiredIds = getAppComponents(args.parentState.groupContext.extensions) ?? []` — derived from the PARENT (pre-commit) state, which is the whole point of Pitfall 2
3. Run `validateAppComponentIntegrity` with `currentExtensions = args.parentState.groupContext.extensions`, `resultingExtensions = args.resultingState.groupContext.extensions`, plus the two values above; return its violation if any
4. `const resultingMemberAccounts = getGroupMembers(args.resultingState)` — import from `../group-members.js`; this returns the hex account pubkeys of every basic-credential leaf in the resulting ratchet tree, which is exactly MDK's "surviving current leaves plus added leaves by account" set, already computed for us by the post-apply state (D-08)
5. Run `validateAdminLeafCoupling` with the same current/resulting extensions and `resultingMemberAccounts`; return its violation if any
6. Return `undefined`

Document in the JSDoc that each seam supplies its own disposition for a returned violation — throw on send (D-02), `rejected` with the violation's `reason` on inbound (D-03), drop the candidate edge on convergence/replay (D-04/D-09) — and that the adapter itself is seam-agnostic.

Then add `export * from "./integrity.js";` to `src/core/components/index.ts`, placed after the `./admin-policy.js` line so the dictionary/codec ordering of the barrel is preserved.
</action>
