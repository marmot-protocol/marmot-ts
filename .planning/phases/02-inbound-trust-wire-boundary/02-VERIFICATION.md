### Gaps Summary

Two of the three roadmap success criteria have a confirmed, unresolved defect directly inside code this phase wrote:

1. **1059 `p`-tag cardinality was never implemented**, despite being explicitly named in ROADMAP.md's success criterion #3 for this phase and encoded in the `TAG_CARDINALITY` table this phase itself created. All three plans' `must_haves.truths` silently omitted 1059 `p` from their scope (each plan only committed to 445 `h`, 444 `e`/`relays`, or 30443 `d`/`i`/`mls_protocol_version`), which is a scope reduction below the roadmap contract that the verification process is required to catch regardless of what the plans self-declared. The code review (02-REVIEW.md IN-01) flagged this gap and it was never closed in a later plan or fix commit.

2. **The 445 drain's dedup-before-verify ordering bug (WR-01)** lets an attacker forge a same-id, corrupted-signature copy of a legitimate group message to poison the `seen` set, silently censoring the genuine message when it later arrives — the genuine event never even reaches the verify gate. This is a direct instance of "forging trust in an unverified field" (the event id, trusted for dedup before any verification), which is the exact failure mode the phase's goal statement says should no longer be possible. Code review flagged this as "worth fixing before ship"; it remains unfixed.

A third, lower-severity but still real regression (WR-02: `createWelcomeRumor`'s relay-URL producer doesn't dedup, while the phase's own strict `getListTag` consumer rejects duplicates) means this phase can make its own producer's output un-joinable by its own consumer. This did not independently drive the `gaps_found` status (it is not explicitly named in the three roadmap success criteria), but it is an unresolved review finding directly caused by this phase's WIRE-02 tightening and should be fixed alongside the two blockers above.

All three issues were identified in `02-REVIEW.md` at the time of code review and remain unresolved in the current codebase — they are not simply present-but-unverified behavior; they are demonstrated, reproducible defects confirmed by direct code reading in this verification pass.

Everything else — the produce-side and inbound KeyPackage Lifetime cap (WIRE-01, fully verified), the 445 `h` / 444 `e`,`relays` / 30443 `d`,`i`,`mls_protocol_version` cardinality gates, and the verify-before-trust ordering on the 1059 and 30443 paths — is genuinely implemented, correctly wired, and covered by passing tests (190/190 across the phase's ten test files; full compile green).
