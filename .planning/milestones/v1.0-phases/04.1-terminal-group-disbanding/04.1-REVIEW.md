## Resolved Findings Archive

### CR-01 [RESOLVED]: Locally published disband commits bypass bounded convergence

**Resolution (019649c):** Fixed. Local pending commits now carry authenticated terminal evidence; publication confirmation retains the edge, leaves the canonical epoch unchanged, and opens the normal immutable bounded pass. Covered by `holds its locally acknowledged disband at the parent until cutoff`.

**File:** `src/engine/group-engine.ts:1248-1305`

**Issue:** `requestDisband()` creates an ordinary `PendingState`, and `GroupRuntime` eventually calls `confirmPublished()`. That method unconditionally installs `pending.newState`, records it as canonical, and returns to `Stable`; it never classifies the commit as disband, calls `#admitDisbandCandidate`, or enters the bounded selection pass. The special admission logic exists only in inbound `ingestEnvelopes`. Consequently the initiating client treats its own acknowledged disband as an ordinary linear commit, contrary to the canonical rule that a valid disband is never terminalized through ordinary linear advancement. It may also emit ordinary member/admin removal notifications for the same commit. CONV-05 is therefore violated on the primary public API path.

**Fix:** Carry authenticated disband evidence on the locally staged pending commit (or reclassify the captured committed proposals against `parentState/newState`) and branch inside `confirmPublished`: retain the commit as a terminal candidate, enter/join the existing immutable convergence pass, and do not call `#setState` or derive ordinary removal notifications until canonical selection. Add an end-to-end `MarmotGroup.disband()` test asserting `Recovering`, unchanged canonical epoch, unchanged pass identity/deadline/scoring, and delayed terminalization after cutoff.

### CR-02 [RESOLVED]: A durable pending request is returned forever instead of regenerated

**Resolution (019649c):** Fixed. Pending intent now re-enters engine preparation on later public calls, after hydration, and after an active selection returns to Stable. Publish failure and restart regeneration are asserted in `disband-request.test.ts`.

**File:** `src/client/group/marmot-group.ts:961-970`

**Issue:** `disband()` returns `{ kind: "pending" }` immediately whenever a durable request already exists. `requestDisband()` is the only method that can regenerate a candidate, and there is no other caller in the codebase. After publication failure, restart, or selection of an active competing branch, every later public `disband()` call exits before regeneration. The request therefore permanently blocks ordinary outbound work while making no progress, directly contradicting LIFE-02's requirement to regenerate against the selected active branch until terminalization or loss of membership/admin authority.

**Fix:** Treat `pending` as intent, not as evidence that a usable candidate exists. Call `session.requestDisband()` for pending requests whenever the engine is eligible to prepare at the current canonical epoch; let its `lastPreparedEpoch`/lifecycle checks deduplicate active work. Also drive the same regeneration after an active convergence winner and after hydration, with tests for publish failure, restart, and losing-disband selection.

### CR-03 [RESOLVED]: Tombstone-first cleanup makes terminal groups impossible to load after restart

**Resolution (019649c):** Fixed. Terminalization persists a scrubbed, non-secret registry shell beside the tombstone before deleting live state. Registry discovery filters live IDs, enumerates terminal tombstones, and treats tombstones as existence authority. Covered by the real cleanup/restart terminal-facade test in `disbanded.test.ts`.

**File:** `src/client/group-registry.ts:186-205`

**Issue:** Terminal cleanup deletes the live state at `src/client/session/group-session.ts:492-503`, but `GroupRegistry.load()` requires that live state before it can construct a session and hydrate the terminal tombstone. Thus, after a normal completed cleanup, `get(groupId)` throws `Group ... not found` and the public read-only `status: "disbanded"`/actor/digest surface disappears on restart. With the default lifecycle adapter backed by the same group-state store, `listIds()` at lines 346-350 additionally attempts `hexToBytes()` on keys such as `<group-id>/disband/terminal`, so `loadAll()` can fail rather than discovering the tombstone. This defeats the durable public terminal contract and permits create/join existence checks to treat the old group id as absent.

**Fix:** Make registry discovery and loading tombstone-aware without requiring serialized live MLS state. Keep a minimal non-secret group registry/index record (or enumerate the dedicated lifecycle namespace) sufficient to construct a read-only terminal facade, filter namespaced keys out of live-state ID enumeration, and reject adoption/rejoin of any group id with a tombstone. Add a restart test that performs real tombstone-first cleanup, creates a fresh client, successfully lists/gets the terminal group, exposes only read-only evidence, and refuses same-id adoption.

### CR-04 [RESOLVED]: Crash during the bounded pass loses terminal meaning and can adopt disbanded MLS state as active

**Resolution (019649c):** Fixed. Candidate identity and immutable pass timing are versioned in the lifecycle namespace and reconstructed from durable history using a restart-safe wall/monotonic clock translation. Hydration enters Recovering and cannot expose the candidate state as Stable. Covered by `restores terminal candidate and immutable pass evidence after a crash`.

**File:** `src/engine/group-engine.ts:346-356,2210-2255`

**Issue:** Exact terminal evidence is stored only in the in-memory `#disbandCandidates` map. The candidate's state/commit may be flushed into `GroupHistoryTree`, but neither the terminal evidence nor the active convergence pass is persisted. On restart, tree reconvergence has no `selectedTerminal` metadata; `#reconvergeFromTree()` can select that tip and `#applyForkResolution()` will transition to `Stable` because `resolution.selectedTerminal` is absent. The client can therefore adopt a state whose authenticated lifecycle component is `disbanded` while exposing it as an active, mutable group with no tombstone. At minimum, a crash also discards the mandatory bounded pass and its fixed cutoff.

**Fix:** Persist terminal-candidate evidence and immutable pass metadata (generation, base epoch, opened/deadline and relevant-input time using a restart-safe clock representation) before acknowledging admission, or encode terminal outcome as authenticated metadata recoverable from each persisted edge and reconstruct a conservative pass on load. Tree resolution must independently recognize a selected tip whose lifecycle transition is a valid disband and refuse to install it as `Stable`. Add crash/restart vectors before cutoff for both winning and losing disband branches.

## Re-review Findings After 019649c

### CR-05 [RESOLVED]: A crash after the tombstone write can still erase the only reloadable registry state

**Resolution (3b5e6cb, ba2fa78):** Fixed and fault-injection verified. Hydration backfills the missing scrubbed registry shell before cleanup; the regression forces the shell write after the tombstone to reject, then proves two fresh registries still discover and load the terminal facade.

**File:** `src/client/session/group-session.ts:475-516`

**Issue:** `persistSelectedDisband()` writes the authoritative tombstone first and the scrubbed `registry-state` second. If the process exits or the second write rejects between them, live MLS state permits one restart. On that restart `#hydrateDisbandTombstone()` finds the tombstone and calls `#cleanupAfterDisband()` directly, without first creating the missing registry shell, and deletes the live state. The following restart has neither live state nor registry shell, so `GroupRegistry.load()` fails. The new test covers only successful completion, not the required crash-after-each-write matrix.

**Fix:** Before any hydration-driven cleanup, idempotently create or verify the scrubbed registry shell. Alternatively persist the shell before making the tombstone authoritative. Add fault injection after the tombstone write and prove two consecutive fresh restart/load cycles retain the terminal facade.

**Resolution (`3b5e6cb`, `ba2fa78`):** Hydration now creates the missing scrubbed shell before cleanup. The regression injects failure at the shell write immediately after tombstone persistence and proves terminal loading across two new registries.

### CR-06 [RESOLVED]: History is exposed before terminal-pass evidence, recreating the crash-restoration ambiguity

**Resolution (9f6493c):** Fixed. Candidate/pass metadata is now a self-contained write-ahead record persisted before history. It includes the authenticated commit and resulting-state material required to reconstruct and later flush a missing edge. The regression rejects the first history write after evidence succeeds, restarts, verifies `Recovering` at the unchanged canonical epoch, and verifies the repaired history commit.

**File:** `src/client/session/group-session.ts:369-375`

**Issue:** `save()` flushes the generic history tree and only afterward calls `persistDisbandConvergence()`. A crash or rejected lifecycle-store write between those awaits leaves a durable disband child in history with no terminal evidence or immutable pass identity. On restart the engine sees no convergence record, cannot restore `Recovering`, and the generic history path may ignore the lone child or later adopt it without `selectedTerminal`, recreating the original disbanded-MLS-as-`Stable` failure. The restart regression manually completes both writes and does not exercise this boundary.

**Fix:** Use a recoverable write-ahead protocol: persist validated candidate/pass evidence before exposing/flushing its history edge and mark completion, or store both atomically. Hydration must fail closed or repair when either half exists alone. Add fault injection precisely between convergence-record and history persistence in both directions.

**Resolution (`9f6493c`):** Save now writes self-contained convergence evidence before history. It contains the encoded commit and resulting state, so hydration reconstructs the candidate and repairs a missing tree edge. The regression injects failure on the first history write, restores `Recovering` at the parent epoch, and verifies the repaired edge persists on retry.
