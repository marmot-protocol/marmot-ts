<objective>
Close the standalone-Add admission gaps and make an Add-proof rejection look identical on every seam (D-05, D-08,
D-09, D-10). Plan 08-01 made the post-apply adapter catch invalid changed leaves. This plan adds the pre-apply
points that must also refuse, and labels them with the same structured violation.
- The admin callback validates every Add, both inside commits and as standalone proposals.
- Inbound ingest stops blanket-accepting standalone proposals.
- The engine's local proposal intent validates raw Adds.
- Outbound commits validate Adds before `createCommit`.
- Callback-level rejections carry `reason: "account-identity-proof"` plus `proofReason` at inbound ingest,
  `resolveCandidateParent` (shared by pool replay and tree-fed convergence), and the history-tree sweep.

Purpose: GRP-04 requires the invitee proof to be validated before anything is proposed or queued. D-04 (plan 08-04)
requires the identical reason and `proofReason` on all four seams. Without this labeling, a pre-apply callback
rejection would surface as `admin-policy` / `authorization_or_components` on inbound and replay, but as
`account-identity-proof` on send, which is exactly the seam asymmetry this phase exists to close.
Output: modified `admin-policy.ts`, `ingest.ts`, `fork-recovery.ts`, `group-engine.ts`; new
`standalone-add-admission.test.ts`; updated gap-pinning tests.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| remote proposer → staged `unappliedProposals` | Any member can publish a standalone Add proposal that a later commit may include by reference |
| local API caller → engine send | Application code can hand-build a `Proposal` and bypass `proposeInviteUser` |
| pooled/forked envelopes → history-tree snapshots | The sweep stages proposals into non-canonical fork snapshots |
