## Implementation Decisions

All Phase 3 decisions **D-01..D-16 remain locked** (see `03-CONTEXT.md`) — in particular:
MDK is authoritative wherever a behavioral choice exists; throw on the send path, typed results
inbound; uniform enforcement at all three seams with no grandfathering; notifications are
delivered via ingest results plus a ledger, **not** via the EventEmitter (D-11); `Infinity` is a
supported `maxRewindCommits` mode, so "cap it" is never an acceptable remedy.

The decisions below are numbered fresh for this phase.

### Notification channel & result union (CR-14, WR-20, WR-18, WR-23)

- **D-01 (LOCKED):** Take **all three at once as one coordinated breaking change** to the public
  result union, rather than three sequential breaks. Add a dedicated *applied-notifications*
  result variant symmetric with the existing `stateInvalidated` withdrawal; wire it from the
  tree-fed rewind path (`#reconvergeFromTree`, WR-20) **and** from locally-authored commits
  (CR-14); ledger-record in both cases. This is the review's own recommendation and it leaves no
  half-wired seam for a round-4 review to find.
- **D-02 (LOCKED):** A locally-authored commit's applied notifications surface **on the confirm
  result, mirroring ingest** — `confirmPublished` exposes the derived notifications and
  `GroupRuntime` forwards them out through the same applied-notifications variant the ingest path
  yields. **`SendResult` is unchanged**, preserving Phase 3's D-02 ("no new `SendResult`
  variant"). Rejected: putting them on `SendResult` at `send()` time, which would announce
  "Alice joined" for a commit that `publishFailed` may still roll back. Rejected: EventEmitter
  re-emission, which reverses Phase 3's D-11.
- **D-03 [trackable] (LOCKED):** **Everything a public signature names must be nameable from the `.`
  entrypoint** — a rule, not a list. That covers `StateNotification`, the new
  applied-notifications variant, `StateInvalidatedIngestResult` (missing from
  `marmot-group.ts`'s curated re-export list), `groupWithdrawnNotificationsByCommit`, and
  `GroupHistoryTree` via `src/engine/index.ts`. Add an **exports-snapshot assertion** so the next
  omission fails a test rather than waits for a reviewer. (Note: `src/__tests__/exports.test.ts`'s
  inline snapshot is already stale from plan 03-01 — see Deferred Ideas; this phase regenerates it.)
- **D-04 [trackable] (LOCKED):** A `deriveStateNotifications` **throw records the digest with an empty
  notification list and logs loudly** — state has already advanced, so the throw cannot fail the
  commit. The digest still enters the ledger, so a later rewind can reach and withdraw the entry;
  it simply withdraws nothing, which is honest (we told the app nothing, we retract nothing).
  **Harmonize both sites** — the new local site *and* the existing WR-15 rewind wrapper, whose
  current `continue` skips `record()` and leaves that link permanently non-withdrawable (the CR-07
  defect through a different door). Rejected: propagating the throw and marking the group
  `Unrecoverable` — far too large a blast radius for a non-protocol concern on already-persisted
  state.

### Ledger bounds under Infinity rewind (WR-02, WR-14 interaction)

- **D-05 [trackable] (LOCKED):** Two structural halves, no cap:
  1. **Digest-keyed index** — `#entries` becomes a `Map` keyed on the digest hex so
     `has`/`record`/`invalidatedByRewind` stop scanning. This is what removes WR-14's O(n)
     `record()`, which CR-14's fix would otherwise roughly double the rate of.
  2. **Tree-derived pruning horizon** — prune to `min(anchorEpoch, oldest epoch still present as
     a tree node)` rather than `anchorEpoch` alone. The fork-history tree is the single persisted
     source (per the full-history design), so this can never prune an entry a candidate branch
     could still name.
  Rejected: the `rewindStore` spill backstop — it adds a persistence path and an async read into
  `invalidatedByRewind`, meaningful new surface area for a phase whose purpose is closing defects.
- **D-06 [trackable] (LOCKED):** **The horizon is a correctness bound, not a memory bound, under `Infinity`.**
  `GroupHistoryTree` has no pruning in v1 by design ("grow all forks for max debugging, prune
  later"), so under `Infinity` the tree-derived horizon still resolves to the root epoch. Ship it
  as correctness; **fix the class doc's false "bounded to the rollback horizon" claim** to state
  what is actually true per mode; and record "unbounded under `Infinity` until the tree itself
  prunes" in `deferred-items.md` as a **known, accepted consequence of the full-history design**,
  not as an open defect. The bound becomes real for free the day tree pruning lands. Rejected:
  giving the ledger its own tree-independent retention, which risks pruning an entry a candidate
  branch could name — exactly what the review warns silently breaks CONV-03's invariant.
- **D-07 [trackable] (LOCKED):** `DeliveredPayloadLedger` gets **both** halves of the same treatment: the
  digest-keyed index + tree-derived horizon, **and** its own-message record gap closed
  (`case "applicationMessage"` on the send path currently records nothing, so a rewind that
  abandons the branch we sent on never retracts our own payload as `invalidated`). Same code
  shape, same defect class as CR-14; splitting them guarantees a future reviewer re-files the
  half we skipped.

### Commit-authorization gate (CR-13, WR-21)

- **D-08 [trackable] (LOCKED):** Switching the send-side gate to the **by-reference union** (what
  `createCommit` actually bundles, and what every peer's inbound gate scans) makes
  previously-succeeding commits **throw**, and that is **documented as a breaking behavioral
  change**. Consistent with Phase 3's D-02/D-14. A commit we can build locally that every
  conformant peer rejects is a programming error, not an expected outcome — throwing is strictly
  better than silently forking off the group. The error states the reason and the caller's
  recourse (wait for the staged proposal to be committed, or have an admin commit). Rejected:
  auto-deferring the self-update, which invents queueing behavior MDK does not have.
  - The affected flow is real and spec-directed: a non-admin calling `selfUpdate()` while any
    foreign proposal is staged is the post-join rotation `refs/marmot/protocol-core/joining.md:58,
    60-64` tells clients to perform.
  - Sanity check carried from the review: switching to the union does **not** break
    `#maybeAutoCommitSelfRemoves`, which only proceeds when `unapplied.every(isSelfRemoveProposal)`,
    so the union stays self_remove-only and still passes.
- **D-09 [trackable] (LOCKED):** **`actorPubkey` is derived from our own leaf inside the gate, on both
  seams** — `getCredentialPubkey(getCredentialFromLeafIndex(state.ratchetTree,
  state.privatePath.leafIndex))`. On a local send the actor is always us; taking it from the
  caller is an opportunity to pass the wrong value, and a gate that can be lied to is not a gate.
  The public intent surface does **not** change. The existing `actorPubkey` on the `commit` intent
  is left in place — planner should check whether it retains any other consumer; removing it if
  fully unused is Claude's discretion.
- **D-10 [trackable] (LOCKED):** The gate is a **pure predicate in `src/core/`**, with both send seams as thin
  adapters — the same treatment Phase 3's D-01 gave the integrity validator, and for the same
  reasons (unit-testable without real MLS state; Phase 4's conformance vectors can drive it
  directly). Rejected: the review's literal `#assertCommitActorAllowed` private engine method,
  which leaves the send rule and the inbound rule as separate code kept in agreement by hand —
  the exact seam-parity failure CR-13 documents. **Not taken in this phase:** refactoring
  `createAdminCommitPolicyCallback` to delegate to the shared predicate — that enters the inbound
  admin gate, which Phase 4's CR-11 work will rewrite (see Deferred Ideas).
- **D-11 [trackable] (LOCKED):** WR-21 — **a malformed leaf is skipped everywhere**. Harden
  `getPubkeyLeafNodeIndexes` and `getPubkeyLeafNodes` with the same `try`/`catch` around
  `getCredentialPubkey` that WR-15 gave `getGroupMembers`, so all three member-enumeration helpers
  agree: a leaf whose credential does not decode is not a member of anything and cannot match a
  pubkey. This unfreezes both commit seams (today a single bad leaf from a Welcome or a
  `ratchet_tree` extension makes `#adminPolicySpliceFor` throw an opaque "Invalid credential nostr
  public key" on every local commit and selfUpdate). Extend
  `src/core/__tests__/group-members.test.ts` with the malformed-leaf case for **all three**
  functions. Rejected: keeping the throw with a better message — the group is still bricked.
